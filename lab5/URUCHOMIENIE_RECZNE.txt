ZMIENNE ŚRODOWISKOWE - CO NAPRAWDĘ TRZEBA USTAWIĆ
  Tylko JEDNA zmienna jest wymagana: CACHE_PREFIX w Scooter Service
  (bez niej usługa się nie uruchomi). Wszystkie pozostałe mają w kodzie
  wartości domyślne, więc zwykle NIE trzeba ich podawać:

    EUREKA_SERVER_URL   domyślnie http://127.0.0.1:8761
    SERVICE_NAME        domyślnie nazwa danej usługi (np. SCOOTER-SERVICE)
    SERVICE_PORT        domyślnie port danej usługi (8101, 8102, 8103, 8104)
    INSTANCE_IP / _HOST domyślnie 127.0.0.1 / localhost
    DATABASE_URL        domyślnie sqlite:///./app.db
    REDIS_URL           domyślnie redis://localhost:6379/0
    RABBITMQ_URL        domyślnie amqp://guest:guest@127.0.0.1:5672/%2F

  Zmienne żyją tylko w konsoli, w której je ustawiono. Zamknięcie okna
  je kasuje (dlatego trzeba je wpisywać za każdym razem, jeśli ich
  potrzebujesz).

KIEDY MUSISZ USTAWIĆ ZMIENNE (a nie polegać na domyślnych):
  - uruchamiasz usługę na INNYM porcie niż domyślny, np. drugą kopię
    Scootera na 8111. Wtedy SERVICE_PORT musi być równe --port. Inaczej
    usługa słucha na 8111, ale w Eurece ogłasza się jako 8101, więc inni
    dostają zły adres i 503.
  - Eureka, Redis lub RabbitMQ stoją pod innym adresem niż lokalny.
  - chcesz inną bazę niż scooter-service\app.db.

CACHE_PREFIX jest wymagany celowo (wymóg z lab 2): Redis może być
wspólny, więc klucze muszą mieć prefiks z numerem albumu. Możesz go
ustawić raz na stałe (zadziała dopiero w NOWYCH konsolach):
    setx CACHE_PREFIX "lab5:131409:scooter-service"
Dla labów 3 i 4 prefiks był inny (lab3:..., lab4:...) - nadpisz go wtedy
zmienną w konsoli.

---------------------------------------------------------------------
 PEŁNA, JAWNA KONFIGURACJA (opcjonalnie)
---------------------------------------------------------------------

Tak wygląda to samo z wszystkimi zmiennymi wypisanymi wprost (tak robi
README i skrypt). Efekt jest identyczny jak z wartościami domyślnymi,
ale widać, co jest skonfigurowane. Przykład dla Scootera:

    $env:EUREKA_SERVER_URL = 'http://127.0.0.1:8761'   # gdzie jest Eureka (bez /eureka)
    $env:SERVICE_NAME      = 'SCOOTER-SERVICE'         # nazwa w Eurece
    $env:SERVICE_PORT      = '8101'                    # MUSI = --port
    $env:INSTANCE_IP       = '127.0.0.1'               # adres dla innych usług (nigdy 0.0.0.0)
    $env:INSTANCE_HOST     = 'localhost'
    $env:DATABASE_URL      = 'sqlite:///./app.db'
    $env:REDIS_URL         = 'redis://localhost:6379/0'
    $env:CACHE_PREFIX      = 'lab5:131409:scooter-service'   # WYMAGANE
    $env:RABBITMQ_URL      = 'amqp://guest:guest@127.0.0.1:5672/%2F'
    .\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8101

Dla pozostałych usług zmieniają się tylko SERVICE_NAME i SERVICE_PORT
(INSURANCE-SERVICE/8103, PAYMENT-SERVICE/8102, MAINTENANCE-SERVICE/8104);
CACHE_PREFIX, DATABASE_URL i REDIS_URL dotyczą tylko Scootera, a
RABBITMQ_URL tylko Scootera, Insurance i Payment.

---------------------------------------------------------------------
 DIAGNOSTYKA - przydatne polecenia
---------------------------------------------------------------------

Co słucha na portach LAB5:
    Get-NetTCPConnection -State Listen -LocalPort 8080,8101,8102,8103,8104,8761,5672 |
        Select-Object LocalPort, OwningProcess | Sort-Object LocalPort

Co widzi Eureka (nazwa -> adres, status):
    curl.exe -s -H "Accept: application/json" http://127.0.0.1:8761/eureka/apps

Kolejki RabbitMQ (ile wiadomości czeka):
    docker exec lab5-rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged

Zabicie procesu zajmującego port (np. 8101):
    Get-NetTCPConnection -State Listen -LocalPort 8101 |
        ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }

Wywołanie usługi BEZPOŚREDNIO (z pominięciem bramki i Eureki) - dobre do
sprawdzenia, czy problem jest w usłudze, czy w routingu:
    curl.exe -i http://127.0.0.1:8101/scooters


---------------------------------------------------------------------
 NAJCZĘSTSZE PROBLEMY
---------------------------------------------------------------------

"CACHE_PREFIX environment variable must be set before start"
    -> nie ustawiłeś $env:CACHE_PREFIX w TEJ konsoli (Scooter Service).

"error while attempting to bind ... port" / port zajęty
    -> stary proces nadal działa. Zabij go (polecenie wyżej) albo
       .\lab5\scripts\stop-lab5.ps1.

503 z bramki zaraz po starcie
    -> rejestr jeszcze się odświeża. Poczekaj ok. minuty.

503 z bramki długo po starcie dla jednej usługi
    -> sprawdź w Eurece, czy ta usługa tam jest i na jakim porcie
       (częsta przyczyna: SERVICE_PORT różny od --port) oraz czy w jej
       konsoli nie ma błędu przy starcie.

500 z bramki po zabiciu usługi
    -> bramka ma w kopii rejestru stary adres (do ok. 90 s).

409 przy tworzeniu hulajnogi/płatności
    -> takie id już istnieje. Zmień id albo zrób reset bazy.

pay zwraca 503 "RabbitMQ broker is unavailable"
    -> RabbitMQ nie działa (docker ps) albo zły RABBITMQ_URL.

Po pay nic się nie zmienia w statystykach
    -> to normalne: konsument działa na żądanie. Wywołaj
       POST /api/scooters/payment-events/consume
       (i /api/insurances/payment-events/consume).

Bramka zwraca 404 bez nagłówka X-Gateway dla nowej trasy
    -> stary jar bramki. Przebuduj (krok 1.4) i uruchom ponownie.
